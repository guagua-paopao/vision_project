# Camera Instance CRUD + PostgreSQL Design

Date: 2026-07-21  
Milestone: M11

## 1. Scope

The public domain resource is a camera instance identified by a stable
`camera_id`. Creating, updating, starting, stopping, and deleting that resource
controls its CPU-only frame-extraction object in the existing
`four_stage_worker`. There is no public Camera Task definition CRUD.

An internal Run record remains necessary for execution audit, frame ownership,
failure recovery, and metrics. Internal C++ names and PostgreSQL table names
still use `CameraTask`/`camera_task_*` in this migration to avoid corrupting the
M0-M10 Run history. They are not public task resources.

Production persistence is PostgreSQL only. SQLite is permitted only in the
one-time legacy import tool and is never linked into Server or Worker.

## 2. Resource and lifecycle contract

| HTTP operation | Durable action | Worker action |
|---|---|---|
| `POST /api/v1/cameras` | insert camera desired state | enqueue START; create extraction object/thread |
| `GET /api/v1/cameras/{id}` | read desired state + Run history | merge Redis hot state |
| `PATCH /api/v1/cameras/{id}` | optimistic update | stop/join old generation, start new generation if enabled |
| `DELETE /api/v1/cameras/{id}` | soft delete | request stop; release subscription; join/reap thread |
| `POST .../{id}/start` | create internal Run | idempotently start thread |
| `POST .../{id}/stop` | mark internal Run stopping | request thread stop |

`camera_id` is supplied by the caller and must contain only ASCII letters,
digits, `_`, or `-`. `run_id` is generated by the server and is never used to
address a camera from the public control plane.

## 3. Thread ownership

`CameraTaskManager::sessions_` is keyed by stable camera id. A control contains
the active Run generation, extraction session, `std::thread`, and completion
flag. When a START for the same camera id carries a new Run id, the manager:

1. calls `requestStop()` on the old extraction session;
2. joins its thread;
3. removes the old control;
4. constructs the new session;
5. starts and registers the new thread.

A duplicate START with the same camera id and Run id is acknowledged without
creating a second thread.

## 4. Shared decode invariant

The extraction thread owns only a FrameHub subscription and JPEG scheduling.
It does not own an FFmpeg decoder. `SharedCameraFrameHubRegistry` remains keyed
by `camera_profile`, so People Flow and all camera extraction threads using the
same Profile share one RTSP reader/decoder. Deleting one camera releases only
its subscription; the Hub closes only after its final subscriber leaves.

## 5. PostgreSQL

Both processes read the DSN from `YOLO11_POSTGRES_DSN`. The value is not stored
in YAML, Redis, HTTP, logs, or Git. Server and Worker initialize the idempotent
schema in `db/postgresql/001_initial_schema.sql`.

PostgreSQL owns durable camera desired state, internal Runs, frame metadata,
People Flow sessions/events/aggregates, and calibration audit. Redis remains
the command, lease, heartbeat, and hot-state transport.

The partial unique index permits only one queued/starting/running/reconnecting
Run per camera. A stopping generation is excluded so PATCH can enqueue its
replacement; Worker-side join still guarantees only one live extraction
thread per camera id.

## 6. Concurrency and failure rules

- PATCH and DELETE require `If-Match` and increment the durable version.
- duplicate START is idempotent;
- thread replacement is serialized by the single Camera command consumer;
- a failed replacement leaves the new Run `failed` and never resurrects the
  deleted/disabled camera;
- a PostgreSQL outage fails readiness and rejects new durable mutations;
- an extraction encode/write error remains isolated from People Flow;
- RTSP URI and database credentials never enter request bodies.

## 7. Removed public capabilities

- `/api/v1/camera-tasks` routes are not registered;
- Camera Profile POST/PATCH/DELETE routes are not registered;
- the operator console has no Task CRUD or Profile mutation controls.

Profile metadata remains deployment configuration and is available read-only
so operators can select a source for a camera instance.
