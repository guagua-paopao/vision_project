| 项目 | 内容 |

| 文档版本 | v1.0 |

| 适用系统 | Vision Project Server / Worker / RTSP / TensorRT / PostgreSQL / Redis / Callback |

## 2. 优化目标

性能优化的总体目标是：

1. 在现有双摄像头、每路目标 10 FPS 条件下稳定达到接近满帧处理；
2. 降低任务替换、排队等待和端到端处理时延；
3. 解耦 GPU 推理与 CPU、磁盘、数据库、Redis、Callback 等慢路径；
4. 提高单机可承载摄像头数量，同时保持有界队列和实时性；
5. 为模型输入尺寸、精度模式、算法级联和动态帧率建立可量化的 A/B 测试体系；
6. 建立可持续使用的分阶段性能指标，避免仅以 CPU、GPU 平均利用率判断瓶颈。

## 4. 目标指标

### 4.1 第一阶段目标：双路稳定满载

| 指标 | 基线 | 第一阶段目标 |
|---|---:|---:|
| 每路平均推理 FPS | 9.361 / 9.425 | ≥ 9.8 / 9.8 |
| 聚合推理 FPS | 18.791 | ≥ 19.6 |
| 目标达成率 | 93.61% / 94.25% | 每路 ≥ 98% |
| 任务替换率 | 6.02% | ≤ 2% |
| Failed jobs | 0 | 0 |
| Stale results | 0 | 0 |
| 30 分钟重连 | 0 / 0 | 0 / 0 |
| 推理耗时 P95 | 14.614 / 14.087 ms | 每路 ≤ 12 ms |

### 4.2 第二阶段目标：端到端时延

端到端指标必须在完成分阶段埋点后正式启用。建议验收线：

| 链路区间 | 目标 |
|---|---:|
| 解码完成 → 推理任务提交 P95 | ≤ 10 ms |
| 推理队列等待 P95 | ≤ 10 ms |
| 任务提交 → 推理结果完成 P95 | ≤ 25 ms |
| 解码完成 → 跟踪/规则结果 P95 | ≤ 150 ms |
| 解码完成 → PostgreSQL 持久化 P95 | ≤ 250 ms |
| JPEG任务排队 P95 | ≤ 100 ms |
| Redis状态发布 P95 | ≤ 50 ms |

Callback 受到外部网络和接收端影响，应单独记录本机出站耗时与接收端确认耗时，不与内部算法链路混合计算。

### 4.3 第三阶段目标：容量扩展

容量测试按 2、4、6、8 路逐级执行，不预先假定增加 Worker 一定带来线性收益。每一级必须满足：

- 每路目标达成率不低于 95%；
- 任务替换率不高于 5%；
- GPU 平均利用率建议不高于 80%；
- GPU 峰值利用率不持续高于 90%；
- GPU 显存不高于物理显存的 80%；
- CPU 平均利用率不高于 70%；
- 不出现持续增长的队列；
- 端到端 P95 不超过对应阶段验收线；
- 30 分钟短测通过后，执行不少于 8 小时的容量稳定性测试。

最大支持路数应由实测确定，不在未测试前写死。

## 5. 优化范围

### 5.1 纳入范围

本计划纳入以下性能方向：

- RTSP 接收、解码、颜色转换和帧内存管理；
- FrameHub 最新帧分发与通知机制；
- 摄像头推理帧率调度；
- 摄像头到 Worker 的负载分配；
- 推理任务队列、背压和任务替换策略；
- CUDA 预处理、TensorRT、D2H 和后处理；
- 检测、Pose、跟踪和规则算法的运行频率；
- ROI、输入尺寸、FP16、INT8、Batch 等模型执行策略；
- 渲染、快照、JPEG 编码和磁盘写入；
- PostgreSQL 连接、查询、事务和写入频率；
- Redis 热状态发布频率与命令合并；
- Callback 消费并发和 HTTP 连接复用；
- 性能指标、压测工具、报告和容量模型。

### 5.2 不纳入范围

以下内容不属于本性能计划的主体：

- 新增业务算法或告警类型；
- 修改现有业务计数和规则定义；
- UI 功能和视觉样式重构；
- 与性能无关的接口协议变更；
- 纯安全加固；
- 未经标注数据验证的准确率调参；
- 为追求吞吐而取消任务幂等、告警持久化或有界背压。

算法模型、输入尺寸、量化方式和推理频率允许作为性能实验项，但必须通过准确率回归门槛。

## 6. 优化原则

所有实现必须遵守以下原则：

1. 实时链路使用有界队列，不允许通过无限排队换取表面零丢帧；
2. 摄像头帧优先保留最新数据，过期任务应可识别并丢弃；
3. 跟踪、计数和时序规则必须保持逐摄像头有序；
4. GPU 推理线程不得同步等待磁盘、数据库、Redis 或 HTTP；
5. 控制面状态更新不得阻塞取帧和推理调度；
6. 每项优化必须支持关闭或回退到基线实现；
7. 不接受只提高平均值、但显著恶化 P95/P99 的优化；
8. 算法性能优化不得在无标注验证的情况下默认接受准确率下降；
9. 所有性能结论必须来自可复现脚本和保留的原始采样数据；
10. 一次实验原则上只改变一个主要变量。

## 7. 分阶段工作包

### 7.1 PERF-OBS：分阶段性能观测

目标：建立能够解释完整链路耗时的指标体系。

需要增加的时间点：

```text
RTSP接收
→ 解码完成
→ FrameHub发布
→ Pipeline读取
→ 推理任务提交
→ Worker出队
→ GPU预处理完成
→ TensorRT完成
→ D2H完成
→ CPU后处理完成
→ 跟踪/规则完成
→ 快照编码完成
→ PostgreSQL完成
→ Redis状态完成
→ Callback完成
```

实施内容：

- 使用 `steady_clock` 记录进程内时间；
- GPU阶段使用 CUDA Event，不使用CPU调用返回时间代替GPU执行时间；
- 每路输出 P50、P95、P99、最大值；
- 记录队列深度、排队时间、替换原因和丢弃阶段；
- 记录每个 Worker 的忙碌率和摄像头分配情况；
- 增加每分钟和完整测试窗口汇总。

完成标准：

- 任一任务可计算完整阶段瀑布；
- 可区分调度延迟、排队延迟、模型耗时和后处理耗时；
- 现有30分钟脚本能够自动生成阶段汇总。

### 7.2 PERF-SCHED：事件驱动帧率调度

目标：消除固定 5 ms 轮询带来的唤醒抖动和累计误差。

实施内容：

- 使用绝对时间 `wait_until(next_due)`；
- FrameHub发布新帧时通知订阅者；
- 新帧到达或下一分析时间到达时唤醒；
- 状态发布与停止检查移出高频调度循环；
- 记录 `scheduled_at`、`submitted_at` 和调度延迟；
- 保持最新帧优先和过期帧丢弃。

完成标准：

- 双路空载调度平均达到至少 9.95 FPS；
- 调度延迟 P95 ≤ 5 ms；
- 无忙轮询导致的明显CPU增长；
- 不改变现有停止、重连和最新帧语义。

### 7.3 PERF-PIPE：推理与后处理流水线化

目标：推理 Worker 完成模型后立即处理下一任务，不同步等待慢路径。

建议结构：

```text
Inference Worker
    ↓ 有界结果队列
Per-Camera Ordered Analytics Executor
    ├─ Status Coalescer → Redis
    ├─ Persistence Queue → PostgreSQL
    └─ Snapshot Queue → Render/JPEG/Disk
```

实施内容：

- 推理结果进入有界 Analytics 队列；
- 同一摄像头结果顺序处理；
- 不同摄像头可并行处理；
- Redis状态只保留最新待发布状态；
- 普通分析结果只保留最新待持久化状态；
- 告警事件不得被普通状态合并覆盖；
- 快照队列设置每摄像头容量和降级规则。

完成标准：

- 推理 Worker 不调用磁盘、PostgreSQL、Redis 和HTTP；
- 双路聚合推理 FPS ≥ 19.6；
- 任务替换率 ≤ 2%；
- 后处理队列无持续增长；
- 告警事件计数与基线一致。

### 7.4 PERF-DB：PostgreSQL连接与写入优化

目标：消除高频建连和重复查询。

实施内容：

- 引入固定容量连接池或每线程长连接；
- 配置连接、语句和事务超时；
- 缓存可复用的 Prepared Statement；
- Run不可变元数据在 Session 初始化时加载并缓存；
- 状态更新按频率或变化合并；
- 必要时使用批量写入；
- 分别记录建连、取连接、执行和提交耗时。

完成标准：

- 稳态处理期间不再为每次状态更新执行 `PQconnectdb`；
- 双路常规状态路径数据库新建连接数接近0；
- 连接池等待 P95 ≤ 5 ms；
- 数据库写入 P95 达到第二阶段目标；
- 数据库结果与基线一致。

### 7.5 PERF-REDIS：热状态发布优化

目标：降低同步Redis命令数量和互斥串行等待。

实施内容：

- 分析状态以内存更新为主；
- 常规状态按 2～4 Hz 合并发布；
- 状态变化、错误和告警允许立即发布；
- 使用 Pipeline 或 Lua 合并 `HSET` 与 `EXPIRE`；
- 调度、分析和控制命令使用独立连接；
- 记录队列等待、网络往返和失败指标。

完成标准：

- 常规分析状态命令数量较基线下降至少 60%；
- Redis发布不在推理线程执行；
- 状态最大可见延迟不高于 500 ms；
- 停止、租约和错误状态不受降频影响。

### 7.6 PERF-SNAPSHOT：渲染、JPEG和磁盘优化

目标：避免快照生成影响推理和跟踪。

实施内容：

- 快照任务独立排队；
- 每路只保留最新普通快照；
- 告警快照单独保证；
- 降低不必要的全分辨率 Mat 克隆；
- 比较 OpenCV JPEG、TurboJPEG、nvJPEG；
- 测试 JPEG 质量 80、85、90；
- 测试原分辨率、1280×720和960×540；
- 复用同一帧的普通快照和分析快照结果；
- 最新图片使用原子发布。

完成标准：

- JPEG和磁盘耗时不计入推理 Worker服务时间；
- 普通快照队列不持续超过1；
- 告警快照无遗漏；
- 画面内容和标注与基线一致。

### 7.7 PERF-ALG：算法执行策略优化

目标：以更少的模型计算维持相同或更高的有效分析帧率。

实验方向：

1. 检测与跟踪采用不同帧率；
2. 普通人员检测与Pose按需级联；
3. 仅对ROI或候选人员执行Pose；
4. 无人或低运动场景降低推理频率；
5. 事件候选出现时临时提高推理频率；
6. 对比640、576、512输入尺寸；
7. 评估每N帧检测、其余帧由跟踪预测的方案。

建议实验矩阵：

| 实验 | 检测 FPS | 跟踪 FPS | Pose策略 | 输入尺寸 |
|---|---:|---:|---|---:|
| ALG-A 基线 | 10 | 10 | 每个推理帧 | 640 |
| ALG-B | 8 | 25 | 每个检测帧 | 640 |
| ALG-C | 5 | 25 | 每个检测帧 | 640 |
| ALG-D | 10 | 10 | 候选ROI按需 | 640 |
| ALG-E | 10 | 10 | 每个推理帧 | 576 |
| ALG-F | 10 | 10 | 每个推理帧 | 512 |

完成标准：

- 必须使用固定回放视频进行A/B；
- 关键准确率指标下降不超过1个百分点，或达到另行批准的阈值；
- 人流计数、轨迹和事件结果不得因乱序产生差异；
- 记录每路GPU时间、CPU时间和有效输出FPS；
- 没有标注数据时，模型尺寸、量化和自适应帧率实验不得进入默认配置。

### 7.8 PERF-TRT：TensorRT执行优化

目标：降低单次推理延迟并提高GPU并行效率。

实施与实验内容：

- 确认当前Engine精度模式；
- 建立FP32、FP16和INT8基准；
- 每个Worker使用独立双缓冲；
- 使用CUDA Event精确计时；
- 评估CUDA Graph；
- 评估GPU Decode/NMS；
- 只回传最终检测结果，减少D2H数据量；
- 评估共享Engine、独立ExecutionContext；
- 对比双Context并发与Batch=2微批处理。

完成标准：

- 单模型P95不高于当前4.236 ms基线，或明确解释输入和精度差异；
- 真实双路推理P95达到第一阶段目标；
- GPU利用率提高时，端到端P95不得恶化；
- INT8和输入尺寸变化必须通过准确率回归。

### 7.9 PERF-DECODE：硬件解码和GPU零拷贝

目标：为多路摄像头扩展消除CPU颜色转换和大帧内存搬运。

实施路径：

1. 记录当前FFmpeg管道吞吐、CPU时间和复制字节数；
2. 评估摄像头子码流作为算法输入；
3. 评估 in-process libavcodec；
4. 评估NVDEC硬件解码；
5. NV12直接进入GPU预处理；
6. 仅在渲染或保存时生成BGR图像。

完成标准：

- 相同路数下CPU解码占用显著下降；
- H2D字节数显著下降；
- 端到端延迟和抖动不高于基线；
- 断流重连能力与现有实现一致；
- 在双路收益不足时不得强制替换稳定实现。

### 7.10 PERF-CALLBACK：Callback吞吐优化

目标：启用Callback后不影响内部分析链路。

实施内容：

- WinHTTP Session和Connection按Profile复用；
- 允许配置有限并发消费者；
- 保留Outbox、幂等和重试语义；
- 新Outbox写入时主动唤醒消费者；
- 轮询作为兜底；
- 单独记录排队、DNS/连接、发送、响应和数据库完成耗时。

完成标准：

- Callback线程与推理线程完全解耦；
- 外部接收端变慢时不降低推理FPS；
- Outbox队列可观测；
- 重试、死信和幂等测试通过。

## 9. 测试与实验方法

### 9.1 三层测试体系

每项优化至少选择适用的测试层级：

1. 微基准：单模型、单阶段或单组件；
2. 固定回放：使用相同视频、相同算法配置，可比较准确率和速度；
3. 真实链路：真实RTSP、PostgreSQL、Redis、磁盘和Callback。

只使用真实直播画面无法保证前后输入完全一致，因此涉及算法和模型的A/B结论必须同时包含固定回放结果。

### 9.2 标准测试窗口

- 预热：不少于60秒；
- 快速回归：5分钟；
- 正式性能测试：30分钟；
- 容量稳定性测试：不少于8小时；
- 生产长稳确认：建议24小时。

### 9.3 必须保留的数据

- 测试配置快照；
- Git提交或工作区差异标识；
- 模型文件SHA-256；
- 硬件、驱动、CUDA、TensorRT和OpenCV版本；
- 每5秒或更细的JSONL采样；
- 汇总JSON；
- P50、P95、P99和最大值；
- 每路FPS、队列深度、替换量和失败量；
- CPU、内存、GPU、显存、温度和磁盘指标；
- 原始日志与测试起止时间。

### 9.4 A/B判定规则

性能优化进入默认配置必须同时满足：

- 目标性能指标达到验收线；
- 至少重复3轮，结论方向一致；
- P95和P99没有不可接受退化；
- 没有新增失败、重连和持续队列增长；
- 算法变化通过固定数据集准确率回归；
- 资源增量与收益比例合理；
- 提供明确回滚方式。

## 10. 配置与变更控制

每项高影响优化应提供独立配置开关，例如：

- `scheduler.mode = polling | event_driven`
- `analysis.pipeline_async = true | false`
- `analysis.status_publish_fps`
- `analysis.input_size`
- `analysis.precision = fp32 | fp16 | int8`
- `analysis.micro_batch_size`
- `analysis.detection_fps`
- `analysis.tracking_fps`
- `analysis.pose_mode = always | roi | candidate`
- `capture.decode_backend = ffmpeg_process | libav | nvdec`
- `snapshot.encoder = opencv | turbojpeg | nvjpeg`

配置名称可在实现阶段调整，但必须满足：

- 默认值明确；
- 可恢复到当前基线行为；
- 配置进入测试报告；
- 不允许无法区分A/B行为的隐式自动切换。

## 11. 风险与约束

| 风险 | 影响 | 控制方式 |
|---|---|---|
| 异步流水线导致逐摄像头乱序 | 跟踪和计数错误 | Per-Camera有序执行器 |
| 队列过大降低表面丢帧但增加延迟 | 实时性恶化 | 有界队列、记录队列年龄 |
| Batch等待其他摄像头 | 单帧延迟上升 | 设置最大组批等待时间 |
| 降低输入尺寸 | 小目标准确率下降 | 固定标注集回归 |
| INT8量化 | 检测和关键点精度下降 | 现场校准集和准确率门槛 |
| 自适应推理FPS | 短时事件漏检 | 运动检测、最小FPS和事件升频 |
| 数据库异步写入 | 进程退出前数据未提交 | 有界持久化队列和停止排空 |
| Redis状态降频 | UI状态更新变慢 | 状态变化立即发布 |
| NVDEC实现复杂 | 开发周期和兼容性风险 | 保留现有后端，可配置切换 |
| GPU利用率提高 | P99抖动、温度和功耗上升 | 设置资源水位和容量余量 |

## 12. 交付物

每个工作包完成时至少交付：

- 实现代码；
- 单元测试或组件测试；
- 可复现的基准脚本；
- 优化前后A/B汇总；
- 原始采样数据；
- 配置说明；
- 回滚说明；
- 已知限制；
- 更新后的性能基线报告。

Phase 1、Phase 3和Phase 5结束后应分别形成版本化性能基线，不覆盖历史数据。

## 13. 性能优化完成定义

单个优化项只有同时满足以下条件才可标记为完成：

1. 优化目标和影响阶段明确；
2. 指标埋点能够证明优化发生在哪一阶段；
3. 同条件A/B测试达到预定收益；
4. 单元、组件和完整链路测试通过；
5. 没有通过无界队列或降低处理语义制造虚假吞吐；
6. 模型或算法变化通过准确率回归；
7. 资源占用变化已记录；
8. 配置、报告和回滚方式齐全；
9. 代码差异通过评审；
10. 新结果已登记为新的候选基线。

整个性能优化计划完成的最低条件：

- 双路每路平均推理FPS ≥ 9.8；
- 聚合推理FPS ≥ 19.6；
- 任务替换率 ≤ 2%；
- 端到端P95达到第二阶段目标；
- Callback启用后不降低内部推理吞吐；
- 24小时稳定测试通过；
- 完成至少2、4、6、8路容量梯度测试，确定单机建议上限；
- 形成最终容量配置建议和性能基线报告。
