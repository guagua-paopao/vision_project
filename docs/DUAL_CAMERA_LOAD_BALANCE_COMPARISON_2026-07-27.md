# 双 Worker 动态均衡优化与双路 10 FPS 复测报告

## 1. 结论

本次已完成以下两项工作：

1. 将摄像头到推理 Worker 的固定哈希分片，改为按当前已分配摄像头数量选择最空闲 Worker；
2. 在相同双路 RTSP、每路目标 10 FPS 的条件下，重新执行 30 分钟完整链路测试。

优化后测试通过预设验收线：两路实际推理吞吐分别为 9.361 FPS 和 9.425 FPS，目标达成率分别为 93.61% 和 94.25%；30 分钟内无重连、推理失败、业务处理失败或健康违规。

与优化前相比：

- 聚合推理吞吐由 13.137 FPS 提升到 18.791 FPS，提升 43.04%；
- 摄像头 `1` 吞吐提升 36.90%；
- 摄像头 `1dsa` 吞吐提升 49.60%；
- 任务替换率由 34.27% 降到 6.02%，相对下降 82.44%；
- 两路吞吐差距由 0.538 FPS 收敛到 0.064 FPS。

## 2. 动态均衡实现

原实现使用摄像头任务 ID 的 FNV 哈希对 Worker 数量取模。当前两个任务 ID 恰好都映射到 Worker 0，导致 Worker 1 基本空闲，双 Worker 实际退化为单 Worker。

优化后的分配策略：

- 摄像头首次提交任务时，选择当前已分配摄像头数量最少的 Worker；
- 负载相同时使用轮转方式选择，避免总是偏向 Worker 0；
- 摄像头运行期间保持 Worker 亲和性，避免推理状态在 Worker 间频繁迁移；
- 摄像头 detach 后释放分配计数，后续摄像头可重新利用该 Worker；
- 推理池停止时清理全部分配状态。

该策略解决了本次两个任务哈希碰撞的问题。它属于“动态初次分配 + 稳定亲和”，并不是根据瞬时队列延迟持续迁移摄像头。

## 8. 回归验证

已增加针对原冲突任务 ID 的回归测试，验证：

- 两个原先会哈希碰撞的摄像头会被分配到不同 Worker；
- 同一摄像头在运行期间保持 Worker 亲和性；

本地测试结果：

- 集成环境未配置的 11 项测试按既有规则跳过，无失败。

## 9. 后续建议

当前结果已经满足“每路至少 9 FPS”的验收线，但距离稳定满 10 FPS 仍有约 5.8%～6.4%差距。建议后续按优先级继续：

1. 为 `worker dequeue → TensorRT → 跟踪/规则 → 渲染/JPEG → PostgreSQL/Redis` 增加分阶段耗时；
2. 将可并行的持久化、快照编码或回调准备移出推理 Worker 同步路径；
3. 对摄像头负载差异较大的场景，把“按摄像头数量最少”升级为按队列等待时间或移动平均处理耗时分配；
4. 执行 8～24 小时双路稳定性测试，重点观察工作集、数据库连接和告警表增长；
5. 启用 Callback 后补测真正到 HTTP 接收端的端到端时延；
6. 算法准确率需要带标注真值的数据集计算 Precision、Recall、F1/mAP，本轮性能测试不对准确率作结论。
